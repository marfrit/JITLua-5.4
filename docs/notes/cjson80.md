# lua-cjson test 80 under JITLua (2026-11-20)

Result: **not a JITLua defect and not a lua-cjson defect.** Test 80 fails only
when the generated `utf8.dat` fixture is missing, and it fails identically
under PUC Lua 5.4.9 and under JITLua `-joff` / `-jon`, on x86_64 and arm64.
No interpreter change and no VM change.

Box wrappers used (both exist):
`~/.local/bin/x64-box -t <s> <cmd>` (x86_64 pool) and
`~/.local/bin/arm-box -t <s> <cmd>` (arm64); no build or test on pica itself.

## Where lua-cjson comes from

- `tests/corpus-ext/manifest.tsv`: `lua-cjson 2.1.0.14`,
  `.dlcache/lua-cjson-2.1.0.14.tar.gz`,
  sha256 `14cac5c7a4520b33449a1fc961344556b8b6a2a2c6b739b0e46e3002e6e605bc`.
- Built from `lua_cjson.c strbuf.c fpconv.c` with `-DNDEBUG`, once against
  `tests/ref/src/lua-5.4.9/src` (PUC arm) and once against `src/` (JITLua), as
  `cjson.so` in the per-family module directory.
- Suite: `tests/test.lua` with `LUA_PATH='../lua/?.lua;;'`.

Test 80 is:

```lua
{ "Decode all UTF-16 escapes (including surrogate combinations)",
  json.decode, { testdata.utf16_escaped }, true, { testdata.utf8_raw } },
```

`testdata.utf16_escaped` is generated in Lua (`gen_utf16_escaped`), but the
expected value `testdata.utf8_raw` is read from `tests/utf8.dat`, a file that
the release archive does not ship. `tests/genutf8.pl` generates it with Perl
`pack("U*", 0..0xD7FF, 0xE000..0x10FFFF)`; the file must have MD5
`cff03b039d850f370a7362f3313e5268` (4382592 bytes). When the file is absent,
`load_testdata` substitutes the literal string
`"Failed to load utf8.dat - please run genutf8.pl"`, which test 80 then
compares against the decoded string and fails.

## Evidence

### Without `utf8.dat` (the `tests/bench/gc_measure.py` path)

`gc_measure.py` unpacks the archive and builds the module, but never runs
`genutf8.pl`; `tests/corpus-ext/run.sh` does (and ignores a missing perl). The
benchmark therefore runs the suite without the fixture on every arm. x86_64
(pve2) and arm64 (escher):

| arm | rc | test 80 | suite |
|---|---|---|---|
| PUC 5.4.9 | 1 | FAIL | 1/105 failed |
| JITLua `-joff` | 1 | FAIL | 1/105 failed |
| JITLua `-jon` | 1 | FAIL | 1/105 failed |

The failure body is identical under all three arms:

```
==> Test [80] Decode all UTF-16 escapes (including surrogate combinations): FAIL
[Expected:success] { "Failed to load utf8.dat - please run genutf8.pl" }
```

`diff` of the PUC and `-jon` outputs shows only the known, implementation-defined
keys order in `pairs` output (table key order, see
`docs/notes/downstream-2026-11.md` §4), no test-80 difference.

### With `utf8.dat` generated by `perl genutf8.pl`

Same source, same builds, same arms; x86_64 and arm64:

| arm | rc | test 80 | suite |
|---|---|---|---|
| PUC 5.4.9 | 0 | PASS | all tests succeeded |
| JITLua `-joff` | 0 | PASS | all tests succeeded |
| JITLua `-jon` | 0 | PASS | all tests succeeded |

So the same C module, decoded under the JIT recorder and under the interpreter,
produces the exact `pack("U*")` bytes for every codepoint including all
0xD800/0xDC00 surrogate combinations; the earlier 104/105 rows in
`docs/notes/downstream-2026-11.md` were a missing-fixture artifact of that
round's runner.

## Classification and remedy

- Test-environment artifact: the suite needs a generated fixture that its own
  release archive omits; no interpreter and no cjson difference is involved.
- Remedy in the benchmark: `gc_measure.py` now runs `prepare_corpus`, which
  executes `perl genutf8.pl` in `tests/<top>/tests/` before the suite (the same
  way `tests/corpus-ext/run.sh` does), and exits with a clear `ERROR lua-cjson:
  need 'perl' ...` instead of silently skipping when perl is not on `PATH`.
  Verified through the gc_measure path on x86_64 and arm64: JITLua `-joff` and
  `-jon` both report 105 PASS, "all tests succeeded".
- No `tests/d54` or `tests/capi` red test: there is nothing for the
  interpreter to fix. `docs/DIFFERENCES.md` and `tests/known-bad.tsv` are
  untouched.
