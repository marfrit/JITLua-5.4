# knuc — open items after the 300% speed-default change (2026-11-19)

Branch `knuc` (from `integ5`, merged `integ6`/gcmode and main `f51a7608`).
Finished and committed: the default change, the tests (including a
policy-independent bound for `weak_closure_shapes`), the docs, the measurement
notes, the test-host name scrub.  Gates: ci-box "all stages passed" and
`ci-local --sanitizers-only` OK on both arches, on a tree with main `f51a7608`
merged.  Red-first: `tests/gcmode.sh` fails (7 cases) against a build with
`LUAI_GCPAUSE` back at 200.

Open, in priority order:

1. **A quiet-box arm64 confirmation of the decision table.** The arm64 run at
   `GC_REPS_FORCE=7` was taken at load 6.6 and its `binary-trees` row
   (300 slower) is contradicted by two 11-rep runs in both arm orders
   (300 faster, +6-7%). The 11-rep run that is quoted in the plan was itself
   taken at load 2.3 -> 7.8, so the arm64 `k-nucleotide` and `lpeg` rows carry
   +-15% spread. Re-run the whole table on a quiet arm64 host.
2. **Peak RSS is now the paid cost and is not in the harness.** The default
   moved +34% on binary-trees and +17% on lpeg (x86_64). `tests/bench/classic/
   run.py` reports wall time only; the RSS column in the plan came from
   `tests/bench/gc_measure.py`. Decide whether the classic runner should carry
   an RSS column so a future policy change cannot be made blind to it.
3. **An adaptive pause is untested.** The data supports "raise the pause when
   the workload keeps a large live set and allocates steadily" but no rule was
   implemented or measured; that needs an allocation-rate input and its own
   A/B on both arches.
4. **The corpus workloads have no stock arm in this harness.** A module built
   against the fork's headers will not load in stock LuaJIT 2.1, so lpeg and
   lua-cjson are compared ours-200 vs ours-300 only. A stock-comparable corpus
   arm would need per-family module builds.
5. **Policy-sensitive test bounds.** `tests/d54/weak_closure_shapes.lua` failed
   intermittently at the new default because its iteration bound was calibrated
   to pause 200; it is now 100000 and 25+25 runs are green, and the other nine
   weak tests are 15/15 green each. Any future pause change must re-check these
   bounds -- they measure allocation-driven collection latency, not correctness.
6. **`setpause=500` is untested on x86_64** (arm64 11-rep: binary-trees 1.09,
   k-nucleotide 0.954), i.e. the two workloads still do not share one optimum.
