# x86_64 without GC64 — what breaks, measured 2026-11-19

Task: a build with `LUAJIT_DISABLE_GC64` on x86_64 fails. Reproduced, root
caused, and bounded. All commands ran on an x86_64 build box through the box
wrapper; nothing was built on the development host.

## 1. Red: the reported failure

```
make -j4 CFLAGS=-DLUAJIT_DISABLE_GC64
```

```
./lj_def.h:384:47: error: size of array 'STATIC_ASSERTION_FAILED' is negative
./lj_obj.h:814:1: note: in expansion of macro 'LJ_STATIC_ASSERT'
  814 | LJ_STATIC_ASSERT(offsetof(GChead, gclist) == offsetof(GCproto, gclist));
make[1]: *** [Makefile:743: host/buildvm_lib.o] Error 1
```

`bc74fe00` replaced upstream's

```c
#if LJ_GC64
  uint32_t unused_gc64;
#endif
```

in `GCproto` with an unconditional `uint32_t envuv`. Upstream keeps that 4 byte
hole only in GC64, where `GCRef` is 8 bytes: in the 32 bit GC reference layout
the field moves `GCproto.gclist` from 12 to 16 while `GChead.gclist` stays at
12. The whole build stops at that assert, in a host translation unit, with
nothing pointing at the layout.

## 2. Next failure, with the layout fixed

`src/Makefile` (around line 465) selects the VM by `LJ_FR2`:

```
ifeq (x64,$(TARGET_LJARCH))
  ifeq (,$(findstring LJ_FR2 1,$(TARGET_TESTARCH)))
    DASM_ARCH= x86
```

so an x86_64 non-GC64 build assembles `vm_x86.dasc`, the VM for 32 bit GC
references — not `vm_x64.dasc`. That file carries four 5.4 hunks (`__len`,
`__pairs`) and nothing else of the port:

```
Error: undefined opcode BC_IDIV
make[1]: *** [Makefile:694: lj_vm.S] Error 2
```

Missing there: handlers for `BC_IDIV`, `BC_KI64`, `BC_TBC`, `BC_TBCCLO`, and the
`cont_tbc` and `cont_tailret` subroutines, so `lj_meta.c`'s
`setcont(top+1, lj_cont_tbc)` and `LJ_CONT_TAILRET` would not link either. The
5.4 interpreter work is in `vm_x64.dasc` (649 changed lines) and
`vm_arm64.dasc`; `lj_frame.h` gates the frame tail mark on
`LJ_FR2 && (LJ_TARGET_X64 || LJ_TARGET_ARM64)` and says "Implemented by the x64
(GC64) and arm64 interpreters and their backends".

Not a blocker: the recorder and the x86 backend already carry fork-authored
`!LJ_GC64` branches for the packed `lj_gc_step_jit` argument (`lj_asm_x86.h`,
`lj_gc.h`), `lj_i64.h` keeps the widened 47-bit form behind `LJ_GC64`, the int64
boxes are `GCudata` with a private `udtype` (layout-neutral), and `lj_alloc.c`
already limits x64 non-GC64 to 2 GB (`LJ_ALLOC_MBITS 31`, `MAP_32BIT`).

Conclusion: the object layout was a fork regression and is fixed. Making the
configuration *work* is an interpreter port to a second assembly VM (four
bytecodes, two continuations, plus an audit of every interpreter-level 5.4
semantic change in `vm_x86.dasc`), which is the open question in the STEP.

## 5. No non-GC64 test skips were added

The harness never runs a non-GC64 binary, so there is nothing to skip yet. The
first tests a `vm_x86.dasc` port would have to win are the six `close_*`
(`<close>`, needs `cont_tbc`), six `i64_*`, three `coro_*` and six `call_*`

## 6. Decision taken, and the open ticket

Decision (foreman, 2026-11-19): x86_64 without GC64 is declared unsupported in
the code as well as in the docs. `lj_arch.h` now stops such a build with an
`#error` naming the missing VM pieces, instead of letting buildvm fail with
`Error: undefined opcode BC_IDIV`. The layout fix and `make layout-check` stay
and keep working: the non-GC64 arm of the check sets
`LUAJIT_GC64LESS_LAYOUT_PROBE`, which skips that message and nothing else. The
check is compile-only (GC object headers, no VM, no JIT), so the guard does not
weaken it -- it only stops someone from thinking the configuration builds.

Open ticket B -- port the 5.4 interpreter to the VM for 32 bit GC references
(`vm_x86.dasc`, which `src/Makefile` selects whenever `LJ_FR2` is off), in the
order the build hits it:

1. `build_ins` handlers for `BC_IDIV`, `BC_KI64`, `BC_TBC` and `BC_TBCCLO`.
   `vm_x64.dasc` has the shapes: `BC_IDIV` is a `jmp ->vmeta_arith_vvo`,
   `BC_KI64` is a tagged constant store from `KBASE`, `BC_TBC` and
   `BC_TBCCLO` are `lj_meta_tbcmark` / `lj_meta_tbcclose` calls, the second one
   parking MULTRES in the slot the helper leaves below the call frame and
   re-executing the UCLO through `->vmeta_binop`.
2. The `cont_tbc` and `cont_tailret` subroutines. Both exist in `vm_x64.dasc`
   and `vm_arm64.dasc`; without them `lj_meta.c`'s `setcont(top+1,
   lj_cont_tbc)` and the `LJ_CONT_TAILRET` continuation do not link.
3. Audit of the interpreter-level 5.4 semantics that only `vm_x64.dasc` and
   `vm_arm64.dasc` carry: int64-box-aware equality and arithmetic fast paths,
   the coroutine resume / pcall frame fixes, the `__call` chain, and the frame
   tail mark, which `lj_frame.h` gates on `LJ_FR2 && (LJ_TARGET_X64 ||
   LJ_TARGET_ARM64)` and would have to be re-derived for the single-slot frame
   link of the `LJ_FR2`-less layout.
4. Not part of the gap (already prepared for 32 bit references): the recorder
   and x86 backend branches for the packed `lj_gc_step_jit` argument
   (`lj_asm_x86.h`, `lj_gc.h`), the GC64-only widening of inline integers
   (`lj_i64.h`), the GCudata i64 boxes, and `lj_alloc.c` with
   `LJ_ALLOC_MBITS 31` / `MAP_32BIT`.
5. Gate and first wins: `tests/harness.sh --strict --mode both --corpus
   tests/d54 --timeout 120`, starting from the six `close_*` tests (they need
   `cont_tbc`), the six `i64_*`, the three `coro_*` and the six `call_*` of the
   115 in `tests/d54`. Only then would a GC64-only test need a skip with a
   reason; no d54 test is GC64-specific today.

### After the decision (same day)

`make -j4 CFLAGS=-DLUAJIT_DISABLE_GC64` on an x86_64 box now stops in the first
host translation unit:

```
lj_arch.h:236:2: error: #error "x86_64 without GC64 is not supported by JITLua-5.4:
  the 5.4 interpreter is in vm_x64.dasc, which requires GC64; a non-GC64 x86_64

  cont_tbc and cont_tailret. See docs/DIFFERENCES.md (Platforms)."
```
